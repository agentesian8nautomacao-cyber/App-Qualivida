## 2. Foreign keys / relacionamentos

| Campo | Relação real |
|-------|----------------|
| `boletos.resident_id` | FK → `residents.id` (repo create table) |
| `boletos.unit` | **Sem FK** — texto |
| → users / staff / condominiums / organizations / memberships | **Sem FK direta** |

### Cadeia real encontrada

```
boletos
  ├── resident_id ──► residents.id
  │                      ├── auth_user_id ──► auth.users (via app/migrations)
  │                      └── unit (string)
  └── unit (string, denormalizado; pode divergir do residents.unit)
```

### Cadeia **NÃO** existente (não inventar)

```
boletos → unit_id → units → condominium_id → condominiums
boletos → condominium_id
boletos → organization_id / site_id
boletos → tenant_memberships
```

Prova LIVE: tabelas `units`, `condominiums`, `tenant_memberships` → **ABSENT_OR_DENIED** no PostgREST (404/inexistentes no schema exposto).

|------|--------|
| Path canônico (código) | `original/{boletoId}.pdf` |
| `{boletoId}` | UUID = `boletos.id` |

Parse seguro (conceitual): `name ~ '^original/([0-9a-f-]{36})\.pdf$'` → UUID → `boletos.id` **se a row existir**.

## 7. Conclusão de ownership

### Possível hoje (person-level, transitivo)

```
auth.uid()
  → residents.auth_user_id
  → residents.id
  → boletos.resident_id
  → (opcional) pdf_original_path / id no path Storage
```

Staff:

```
auth.uid()
  → users.auth_user_id + role staff
  → acesso “qualquer boleto do projeto” (sem site)
```

### Impossível hoje (tenant/site Operaut)

```
auth → membership → site → boleto
boleto → condominium_id / site_id
```

**OWNERSHIP = C** para isolamento multi-tenant / multi-site no Storage.

## 8. Estratégia e recomendação

### Classificação formal: **C — OWNERSHIP INSUFICIENTE** (tenant/site)

Não inventar policy Storage do tipo “só tenant X” sem coluna/FK de site.

### Menor mudança estrutural (antes de Storage multi-tenant / ownership fino)

Ordem sugerida (documental; **não** executar aqui):

1. Introduzir **Operational Site** (`condominiums` / M1) e `condominium_id` em `residents` e **`boletos`** (nullable → backfill → NOT NULL).  
2. Popular memberships (M3/M11).  
3. Só então policies Storage com join `boletos` + membership/site **ou** path `…/condominiums/{id}/…`.

### Para R2 **mínima** (fechar bucket público) — sem ownership fino

Ainda viável **sem** resolver C:

- `public=false` + drop `boletos_read_all` + `SELECT` authenticated no bucket  

Isso **não** implementa “morador só o seu PDF” no Storage (qualquer authenticated com o path ainda lê, se souber o UUID). Declarar como **dívida explícita**, não como ownership completo.

### Impacto / riscos

| Risco | Detalhe |
|-------|---------|
| Fingir ownership por `unit` string | Frágil; sem FK; colisão multi-condo |
| Policy Storage só authenticated | Melhora vs público; não isola tenants |
| Path só `original/{id}.pdf` | Sem prefixo de site; vazamento cross-tenant se multi-condo no mesmo bucket |
| `resident_id` NULL | Boletos sem morador: só staff/projeto |
