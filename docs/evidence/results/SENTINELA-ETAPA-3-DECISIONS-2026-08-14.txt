DR3 — IDEMPOTÊNCIA
============================================================
STATUS: CLOSED

RECOMMENDATION:
  1) Header Idempotency-Key OBRIGATÓRIO em POST/PATCH mutáveis.
  2) n8n gera key estável por intenção (preferir hash de wa_message_id
     + operation + condominium_id).
  3) Fingerprint = SHA-256(canonical: method + path + body_sha256 +
     organization_id + condominium_id + operation).
  4) Replay (mesma key + mesmo fingerprint): HTTP 200 + mesmo corpo
     de sucesso previamente persistido (não reexecuta Core).
  5) Mesma key + fingerprint diferente: HTTP 409 DUPLICATE_REQUEST.
  6) GET identify / boletos: Idempotency-Key opcional (não exigida).
  7) Janela de retenção recomendada: 72 horas (piloto); depois purge.
  8) Store DEFINITIVO: PostgreSQL (tabela dedicada no tenant/schema app).

  DATABASE CHANGE REQUIRED — FUTURE MIGRATION
  (ex.: api_idempotency_keys — NÃO criar agora)

  Gate de implementação:
  - Mutações via API em produção só após migration do store.
  - Memória de processo / single-instance = INADEQUADO (rejeitado).
  - Redis/KV = alternativa transitória apenas se migration atrasar;
    destino oficial permanece Postgres.

RATIONALE:
  WhatsApp/n8n reenviam; create_package não é idempotente por natureza.
  Serverless exige store compartilhado. Postgres já é fonte da verdade.

IMPACT:
  Bloqueia writes públicos até migration futura.
  Design e scaffolding de rotas podem ser preparados depois, com
  writes desabilitados até o store existir.

RISK: CRITICAL se ignorado; LOW se gate respeitado

DR4 — AUTENTICAÇÃO (n8n ↔ API)
============================================================
STATUS: CLOSED

RECOMMENDATION:
  Modelo: Integration Credential (NÃO “Bearer SECRET” isolado)

  Headers obrigatórios:
    X-Sentinela-Client-Id
    X-Sentinela-Timestamp          (unix seconds)
    X-Sentinela-Signature         (hex HMAC-SHA256)
    X-Organization-Id
    X-Condominium-Id
    Idempotency-Key               (mutações)
    X-Correlation-Id              (recomendado)
    Content-Type: application/json

  Canonical string (exemplo fechado):
    v1\\n
    {timestamp}\\n
    {METHOD}\\n
    {path_with_query}\\n
    {sha256_hex(body_or_empty)}\\n
    {organization_id}\\n
    {condominium_id}\\n
    {idempotency_key_or_empty}

  Signature = HMAC-SHA256(secret, canonical)

  Anti-replay:
    |now - timestamp| <= 300s
    + Idempotency-Key para mutações
    (nonce dedicado opcional; key cobre mutações)

  Rotação:
    Dois secrets ativos (current + previous) por client_id,
    overlap mínimo 24h; previous revogável.

  REJEITADO:
    Authorization: Bearer <secret_unico> como único fator
    Service role Supabase dentro do n8n
    Segredos no frontend Vite

RATIONALE:
  Simples o bastante para n8n (HMAC em Function node / crypto),
  amarra tenant + body + método, mitiga replay e vazamento parcial.

IMPACT:
  Secrets só em Vercel env + credential store do n8n.

RISK: MEDIUM (implementação incorreta do canonical) — mitigar com testes de contrato

DR5 — TENANT BOUNDARY (FAIL-CLOSED)
============================================================
STATUS: CLOSED

RECOMMENDATION:
  API:
    - organization_id + condominium_id obrigatórios em toda operação.
    - Validar existência e vínculo condo∈org.
    - Validar que credential está scoped EXATAMENTE a esse par.
    - Nunca confiar em tenant “sugerido” pelo texto WhatsApp sem
      cruzar com o escopo da credential.
    - Passar ao Core SEMPRE com OperationContext preenchido.
    - Sem fallback silencioso / sem withPilotTenantDefaults na API.
    - Erros: TENANT_REQUIRED | TENANT_NOT_FOUND | TENANT_MISMATCH → 400/403

  Core (dual-mode fechado):
    - Caller API / channel whatsapp|n8n|system_integration:
      enforceTenant = true → ausência = falha (não warning).
    - Caller painel legado: mantém warning TENANT_CONTEXT_ABSENT
      até App enviar IDs M4 (melhoria de wire — sem migration).
    - PROIBIDO default silencioso para “tenant global”.

  IDs piloto M4 = referência de config/runbook, NÃO hardcode de bypass.

RATIONALE:
  Canal externo sem tenant = vazamento cross-condo (CRITICAL).
  Painel single-tenant legado não pode quebrar de uma vez.

IMPACT:
  Pequena evolução de enforce no Core na implementação da API
  (sem DDL). Wire do App com IDs piloto recomendado em paralelo.

RISK: HIGH se API implementar sem enforce; LOW se gate seguido

DR7 — IDENTIDADE DO MORADOR
============================================================
STATUS: CLOSED

RECOMMENDATION:
  Telefone normalizado = identificador de ENTRADA do canal WhatsApp.
  Nunca autorização suficiente sozinho para operações SENSITIVE.

  Resolução oficial (escopo do condominium da credential):
    telefone_normalizado
      → resident(s) no condomínio
      → unit
      → condominium_id (deve == credential)
      → organization_id (deve == credential)

  Regras:
    0 match → RESIDENT_NOT_FOUND (não executar write)
    1 match inequívoco → OK para fluxo automático elegível
    >1 match OU name_only fraco → AMBIGUOUS_RESIDENT /
       NEEDS_CONFIRMATION — NÃO executar write sensível
    identify_resident.ambiguous=true do Core → API traduz para
       NEEDS_CONFIRMATION (não “success com chute”)

  Confirmação humana (WA): n8n solicita clarificação; nova chamada
  API só após resident_id explícito confirmado.

RATIONALE:
  Core já retorna ambiguous; telefone compartilhado / cadastro sujo
  é risco real de entrega errada.

IMPACT:
  n8n precisa ramo de clarificação; Core identify permanece fonte.

RISK: HIGH se ignorar ambiguidade; LOW se NEEDS_CONFIRMATION enforced

DR13 — CONTRATO DE ERROS
============================================================
STATUS: CLOSED

RECOMMENDATION:
  Envelope:
    { success, request_id, correlation_id?, operation?, error?: { code, message, details? } }

  Códigos canônicos (API):
    INVALID_REQUEST
    UNAUTHORIZED
    FORBIDDEN
    TENANT_REQUIRED
    TENANT_NOT_FOUND
    TENANT_MISMATCH
    RESIDENT_NOT_FOUND
    AMBIGUOUS_RESIDENT
    RESOURCE_NOT_FOUND
    CONFLICT
    NEEDS_CONFIRMATION
    DUPLICATE_REQUEST
    RATE_LIMITED
    INTERNAL_ERROR

  Mapa Core → API (exemplos):
    VALIDATION_ERROR → INVALID_REQUEST
    NOT_FOUND → RESOURCE_NOT_FOUND / RESIDENT_NOT_FOUND
    AUTHORIZATION_ERROR → FORBIDDEN
    DUPLICATE (pickup) → CONFLICT ou código específico PACKAGE_ALREADY_PICKED_UP
      (alias permitido em details.code_original)
    CONFLICT (reserva) → CONFLICT
    CLARIFICATION_REQUIRED / ambiguous → NEEDS_CONFIRMATION
    TENANT_CONTEXT_ABSENT na API path → NÃO vaza como success+warning;
      fronteira bloqueia antes

RATIONALE:
  Contrato estável para n8n branching.

IMPACT:
  Testes de contrato na implementação.

RISK: LOW
