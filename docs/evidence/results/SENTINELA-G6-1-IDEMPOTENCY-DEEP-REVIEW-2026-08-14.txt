4. CENÁRIOS DE IDEMPOTÊNCIA (A–F)
============================================================

A) Tenant A + key X + fingerprint F1 → primeira operação
   PASS (desenho): INSERT sob UNIQUE; status in_progress → completed.
   (Comportamento completo depende do wiring — fora desta migration.)

B) Tenant A + key X + fingerprint F1 → reutilizar
   PASS (desenho): SELECT por UNIQUE key; fingerprint igual → replay response_body.
   Exige wiring: comparar fingerprint; não reexecutar Core.

C) Tenant A + key X + fingerprint F2 → conflito
   PASS (desenho): row existe; fingerprint ≠ → API DUPLICATE_REQUEST.
   DB sozinho NÃO rejeita F2 (não há constraint fingerprint); correto —
   a rejeição é de aplicação sobre a row existente.

D) Tenant B + key X + fingerprint F1 → independente
   PASS: UNIQUE inclui tenant; A e B isolados.

E) Duas concorrentes Tenant A + key X
   PASS (DB): UNIQUE garante no máximo 1 row; segundo INSERT falha (unique_violation).
   Wiring DEVE tratar unique_violation como: re-ler row e aplicar B ou C
   (não como INTERNAL_ERROR cego).

F) Mesmo key após expires_at → nova operação
   FAIL / DIVERGÊNCIA

   expires_at = retenção LÓGICA apenas.
   A UNIQUE (org, condo, key) PERMANECE após expires_at.
   INSERT de nova row com a mesma key → unique_violation PARA SEMPRE
   enquanto a row antiga existir.

   Portanto:
   - expires_at sozinho NÃO cria TTL físico
   - sem DELETE/UPDATE de reclaim, key NÃO é reutilizável após 48h
   - cleanup automático NÃO existe (e não deve ser inventado como cron nesta migration)

   Classificação: DIVERGÊNCIA TTL × UNIQUE (bloqueante para APPROVED).

6. STATUS / RACES / INTEGRIDADE DE RESPOSTA
============================================================
Estados: in_progress | completed | failed
Avaliação: SUFICIENTES para a implementação atual — não adicionar mais.

Riscos:

1) Operação presa em in_progress
   RISCO: MEDIUM
   Se o processo cair após INSERT in_progress, retry com mesma key+F1
   pode ver in_progress sem response_body.
   expires_at=48h é longo demais como lease de execução.
   Correção (wiring, não novo status):
     - lease curto derivado de created_at (ex. 60–120s) para reclaim de in_progress
     - OU usar expires_at só para retenção e lease separado no wiring
   NÃO exigir novo estado "abandoned".

2) Retry indefinido
   RISCO: LOW–MEDIUM se wiring não tratar in_progress.
   Política sugerida: se in_progress e lease válido → 409/503 retry-later;
   se lease expirado → reclaim.

3) completed sem response
   RISCO: MEDIUM — DDL permite status='completed' com response_body NULL.
   Proposta REVISION opcional (CHECK):
     CHECK (
       status = 'in_progress'
       OR (response_body IS NOT NULL AND response_status IS NOT NULL)
     )
   e completed_at NOT NULL quando status IN ('completed','failed').
   Recomendado incluir na revisão SQL antes do APPLY.

4) failed reutilizado incorretamente
   RISCO: MEDIUM — política não definida no DDL.
   Wiring deve decidir:
     failed + mesmo fingerprint → replay erro OU permitir retry (reclaim)
   Documentar uma política; sugerida: replay do erro cacheado até expires_at
   (igual completed), salvo reclaim pós-expiry (R1).

5) Race E
   UNIQUE OK; wiring deve mapear unique_violation → re-get.
