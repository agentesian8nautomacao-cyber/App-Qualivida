4. FINGERPRINT
============================================================
PASS (persistência + contrato canônico; cálculo = API)

Coluna operation_fingerprint text NOT NULL + CHECK nonempty.

Canônico documentado (DR5 / header migration):
  SHA-256("sentinela-confirm/v1\n" + org + "\n" + condo + "\n"
          + operation + "\n" + resource_id)

Consequências do canônico (quando API calcular corretamente):
  ops diferentes     → hashes diferentes     (não colidem)

sem inventar unicidade não decidida). Validate/Consume exigem match na API.

  R-FP-1 — múltiplas rows pending com mesmo fingerprint possíveis
           (sem UNIQUE). DR5/DR11 não exigem unicidade; desafios
           concorrentes do mesmo recurso ficam a cargo do wiring futuro.

7. ATOMICIDADE DE CONSUMO / CONCORRÊNCIA
============================================================
PASS (desenho)

Simulação conceitual Request A || Request B no mesmo confirmation_id:

  Ambos: UPDATE … SET status='consumed', consumed_at=$now
         WHERE confirmation_id=$id
           AND organization_id=$org AND condominium_id=$condo
           AND status='pending' AND consumed_at IS NULL
           AND expires_at > $now
         RETURNING *

  Postgres: row lock na mesma PK.
  Primeiro commit: 1 row → consume OK → Core permitido.
  Segundo: 0 rows → ALREADY_USED / INVALID — Core NÃO.

PK impede duas rows do mesmo id.
Sem store em memória; sem trigger; suporte a UPDATE atômico adequado.

Nota: implementação do UPDATE é gate de wiring — DDL fornece colunas/
CHECKs/PK necessários. Adequado para APPROVED FOR LIVE PRE-CHECK.
