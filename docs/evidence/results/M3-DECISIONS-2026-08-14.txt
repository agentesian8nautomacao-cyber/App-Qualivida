================================================================================

  - User pode ter N memberships (arquitetura + testes M3) — SIM
  - Multi-condomínio — SIM
  - Conceito “membership padrão ao login” — SIM (§5 is_default)
  - Contexto ativo operacional — JWT/session active_membership_id (§ sessão)

Fontes:
  Arquitetura §5 campo is_default
  Plano M3 omite (mínimo) — arquitetura prevalece para campo conceitual listado
  Operaut: membership no site

Rejeitado: omitir “porque sessão resolve” — doc lista o campo; default DB ajuda M4/M11

  (app garante no máximo um is_default=true por auth_user_id)

DR7 — CONSISTÊNCIA ORG ↔ CONDO = CLOSED
================================================================================
Decisão: opção A (variante documentada)

  - MANTER organization_id NOT NULL + condominium_id NOT NULL
  - FK simples para organizations(id) e condominiums(id)
  - NÃO implementar FK composta / CHECK / trigger em M3
  - Invariante documental:
      membership.organization_id
        = (SELECT organization_id FROM condominiums WHERE id = membership.condominium_id)
  - Enforcement: aplicação + M4/M11 inserts corretos
  - Evolução futura (fora M3): FK composta
      (condominium_id, organization_id) → condominiums(id, organization_id)
      exigiria UNIQUE(id, organization_id) em condominiums (= ALTER M1)
      → requer autorização separada

Por que não B agora:
  Composite FK é superior em integridade, mas altera condominiums — escopo M3
  é CREATE tenant_memberships; LEGACY/M1 ALTER = 0

Por que não C (remover organization_id):
  Contradiz plano M3 e arquitetura §5 (organization_id FK NOT NULL)
  Addendum/arquitetura usam org em memberships para escopo org

Exemplo proibido (deve ser impedido por app/M4/M11 até constraint futura):
  Org A + Condo de Org B
