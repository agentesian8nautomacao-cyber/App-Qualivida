## 6. slug decision

Estado atual:
  organizations.slug UNIQUE global
  condominiums.slug UNIQUE global

Perguntas:

1) organization.slug global?
   Recomendação: SIM.
   Motivo: Organization é entidade de plataforma B2B; slug tipicamente
   namespace global (admin URLs, billing, paths). Multi-tenant org-vs-org
   compete no mesmo nível PLATFORM.

2) condominium.slug global?
   Recomendação: NÃO (revisar).

3) condominium.slug único dentro da organization?
   Recomendação: SIM → UNIQUE (organization_id, slug)

Cenário:
  Org A: residencial-xyz
  Org B: residencial-xyz
  Com UNIQUE(slug) global → PROIBIDO
  Com UNIQUE(organization_id, slug) → PERMITIDO

Comparação arquitetura:
  - Hierarquia org 1→N sites; isolamento por organization_id + site id.
  - Storage paths usam UUIDs: organizations/{org_id}/condominiums/{condo_id}/…
    (não dependem de slug global).
  - Padrão análogo M2: UNIQUE (condominium_id, code) — unicidade scoped.
  - Plano M1 teste “UNIQUE slug” é AMBÍGUO (não define escopo).

Severidade: ALTA (design multi-tenant; difícil mudar após M4 seed sem migração).

Recomendação técnica:
  Trocar condominiums_slug_key por UNIQUE (organization_id, slug)
  antes do APPLY. Manter organizations.slug UNIQUE global.
  Atualizar COMMENT da coluna slug do site.

## 8. status decision

Arquitetura:
  - org/condo: coluna status citada; SEM enum de valores.
  - tenant_memberships: active / invited / suspended (outra entidade).

SQL atual: text NOT NULL DEFAULT 'active'; sem CHECK.

Avaliação:
  - Não há enum org/site definido na arquitetura → ausência de CHECK
    é coerente com “não inventar”.
  - Risco: valores livres ('foo') no banco; app precisa validar.
  - Para M1 (tabelas vazias, sem app): risco BAIXO operacionalmente.

Recomendação M1:
  MANTER text sem CHECK (intencional / deferido).
  Documentar no plano valores previstos sugeridos: active | inactive | suspended
  (sem CONSTRAINT até decisão explícita).
  Alternativa (se produto quiser trava já): CHECK status IN (...) — seria
  nova DECISÃO, não requisito atual.

## 9. FK decision

ON DELETE RESTRICT em organization_id:

Prós:
  - Impede exclusão acidental de org com sites.
  - Compatível com M4 (sites passam a ter valor).
  - Rollback M1 puro: DROP tables; RESTRICT não atrapalha (drop filho primeiro).

Contras / futuro:
  - Lifecycle “arquivar org” exigirá soft-delete/status, não DELETE físico.
  - CASCADE seria perigoso demais para M1.

Recomendação: MANTER ON DELETE RESTRICT.
Classificação: DECISÃO adequada.
